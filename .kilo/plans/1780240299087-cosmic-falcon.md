# Plan: Complete Media Upload Integration

## Context

The Media Upload feature has backend API endpoints and frontend UI components already built, but they are not wired into the actual journal writing/editing/viewing flows. The user confirmed:
- Free-form journals use `slide_index = 0` for media attachments
- Local SQLite stores media as a JSON URL array on the `user_journals` row (simplest offline-first approach)

## Goals

1. Add media upload UI to **free-form journal** writing (`pages/journaling/index.vue`) and editing (`pages/journaling/[id].vue`)
2. Wire `MediaUploader` events in **slide-based journal** (`JournalPrompt.vue`, `ModalContents.vue`, `EditModalContents.vue`)
3. Display uploaded images in **journal preview** (`DetailView.vue`) and **history/homepage cards**
4. Persist media URLs locally and sync them with the server

---

## Phase 1: Data Layer — SQLite + Store + Sync

**File:** `services/sqlite/sqlite_service.ts` (or wherever the `user_journals` table is created)

- Add `media TEXT` (JSON string) to the `user_journals` table schema.
- Provide a migration path for existing databases (ALTER TABLE or recreate).

### 1.2 Update `JournalsRepository`
**File:** `services/sqlite/journals_repository.ts`

- `create()`: Accept `media` and persist it.
- `update()`: Accept `media` and persist it.
- `mapRowToJournal()`: Parse `media` JSON string → `Array<{ url: string; alt?: string }>`.
- `syncFromServer()` / `upsertFromServer()`: Handle `media` field from server payload.
- `getById()` / `getAllByUserId()`: Return populated `media`.

### 1.3 Update `userJournalStore`
**File:** `stores/stores/user_journal.ts`

- `createJournal()`: Accept optional `media` in `CreateJournalRequest` and pass to repository.
- `updateJournal()`: Accept optional `media` and pass to repository.
- Add helper: `setJournalMedia(journalId, media)` for in-place updates.

### 1.4 Update `SyncService` / `TranquaraSDK.syncJournal`
**Files:** `services/sync/sync_service.ts`, `stores/tranquara_sdk.ts`

- After a journal is synced to the server (and we have the server `journal_id`), call `POST /api/v1/media/attach` with:
  - `journal_id`: server journal ID
  - `slides`: `[{ slide_index: 0, media_ids: [...] }]` (or per-slide for template-based)
- For free-form, `slide_index` is always `0`.
- For template-based, collect media per slide index from the writing session state.

## Phase 2: Slide-Based Journal Wiring

### 2.1 `JournalPrompt.vue` — handle upload/remove events
**File:** `components/Slide/JournalPrompt.vue`

- Add local state: `attachedMedia: Array<{ id: string; url: string }>`.
- Handle `@uploaded`: push `{ id: mediaId, url: r2Url }` to `attachedMedia`, emit event up.
- Handle `@removed`: remove from `attachedMedia`, emit event up.
- On mount (edit mode): if `initialMedia` prop provided, populate `attachedMedia`.
- Emit `media-change` event so parent knows media for this slide.

### 2.2 `ModalContents.vue` — collect media per slide and pass on save
**File:** `components/Journal/ModalContents.vue`

- Add reactive state: `slideMedia: Map<number, Array<{ id: string; url: string }>>`.
- Listen for `media-change` from `JournalPrompt` child components (via event bus or provide/inject, or pass as prop/emit through the carousel slot — simplest is to use a shared session state like `userJournalStore` or a dedicated composable).
  - **Decision:** Use `userJournalStore` or a new `currentSlideMedia` ref on the store so `JournalPrompt` can write and `ModalContents` can read.
- In `nextNode()` / `saveJournal` call: pass `media` (aggregated per slide) to `useSlideGroup.saveJournal()`.
- After save succeeds: call `attachToJournal` via `useMediaUpload()` to link media IDs to the journal server ID.

### 2.3 `useSlideGroup.ts` — accept media in save
**File:** `composables/useSlideGroup.ts`

- `saveJournal()`: accept optional `media` parameter (or per-slide media array) and include it in `createJournal` call.

### 2.4 `EditModalContents.vue` — load existing media + allow edits
**File:** `components/Journal/EditModalContents.vue`

- Add `MediaUploader` below the editor in the template (same pattern as `JournalPrompt`).
- On mount: parse existing media from `props.journal.media` and pass as `initialMedia` to each slide's `JournalPrompt`.
- On save (`saveJournalChanges`): collect current media state per slide, include in `updateJournal`, then call `attachToJournal` to sync media links.

## Phase 5: Backend Sync & Attach Flow

### 5.1 Ensure `attachToJournal` is called after journal sync
**Files:** `services/sync/sync_service.ts`, `stores/tranquara_sdk.ts`

- When a journal is successfully synced and we receive the server `journal_id`:
  - If the journal has `media` (local URL array), we need the `media_ids` (UUIDs from `MediaFile`).
  - **Problem:** Local `media` only stores URLs, not the backend `media_id`.
  - **Solution:** Store both `id` and `url` in local `media` JSON: `[{ id: "uuid", url: "..." }]`.
  - Update all local media handling to store `{ id, url }` pairs.
- Call `POST /api/v1/media/attach` with the server `journal_id` and collected `media_ids`.

### 5.2 Fetch media on journal load
**File:** `services/sync/sync_service.ts` or `userJournalStore`

- When downloading journals from server (`syncDownloadFromServer`), the server response may include `media` field (or we need to fetch it separately via `GET /api/v1/media/journal/{id}`).
- **Decision:** If server `GetJournals` already returns `media` as a joined array, use it directly. If not, fetch media separately after journal download or include it in the server response.
- Populate local SQLite `media` column with the fetched URLs.

## Phase 6: Polish & Edge Cases

### 6.1 `useMediaUpload` integration
- Ensure `uploadWithProgress` returns `MediaFile` with `id` and `r2_url`.
- Store `{ id: mediaFile.id, url: mediaFile.r2_url }` locally.

### 6.2 Offline handling
- Images uploaded while offline: the upload will fail. Show error toast. User can retry.
- Already-uploaded images viewed offline: `CachedImage` + `useOfflineMedia` handles this automatically.

### 6.3 Edit mode — removing previously uploaded images
- `MediaUploader` emits `@removed` with `mediaId`.
- Call `deleteMedia(mediaId)` to remove from R2 + backend.
- Remove from local state.

### 6.4 i18n
- Use existing keys: `$t('journal.addPhoto')`, `$t('journal.maxPhotosReached')`, etc.

## Open Questions / Risks

1. **Server `GetJournals` response format:** Does it already include `media` array? If not, need backend change or extra API call during sync.
2. **Carousel slot communication:** `ModalContents` uses `UCarousel` with dynamic slots. Passing media state between slides may require a shared store ref or provide/inject rather than prop drilling.
3. **SQLite migration on existing user devices:** Adding a column needs a versioned migration strategy for the Capacitor SQLite plugin.
